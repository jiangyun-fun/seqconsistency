4× more reads moved peak RSS by +0.0 MiB: retained state scales with the sample size and fixed bins, not the read count (long-read sequences are never retained).

Note on absolute values: both scans run in one process, so `ru_maxrss` reports the process-wide high-water mark including earlier stages — the informative quantity is the flat delta. Isolated-process measurements (tests/test_memory.py) show the scanner itself at roughly 0.5 GiB peak for long-read inputs at this batch budget.

## Bottlenecks observed (before any native optimization)

1. FASTQ scanning is bound by the per-record Python bookkeeping (line splitting, batch assembly), not by the vectorized per-base statistics.
2. PE synchronization adds a per-pair name comparison in Python; compare the PE and SE rows above for the measured overhead.
3. BAM scanning is bound by pysam per-record object creation and per-record attribute access (features, clipping, RG check). After the reservoir batching fix it runs at roughly half the vectorized FASTQ rate; before that fix a quadratic reservoir update dominated and made it ~165x slower — a reminder to profile before attributing bottlenecks.
4. Long reads cost ~10× short reads per base in wall time at the same batch budget because per-batch record counts fall; memory stays bounded.

No compiled extensions were introduced: these measurements are the baseline the spec requires before considering native optimization.
